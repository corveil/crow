## [Unreleased]

### Added

- CROW-1163 — **Escape returns to the session grid** when the full session was opened from a grid cell. A `‹ Grid` control appears in the session header (title teaches `Esc` unless the session switcher is bound to an Escape prefix such as `esc+tab`). The binding is capture-phase on `document` but **does not fire while the xterm has focus** — Claude Code and other agents use Escape to cancel, and `web/terminal.js` forwards keystrokes to the PTY, so a global binding would steal it. Overlays (Settings, lightbox, in-page prompts, the session switcher, context menus) keep first refusal. When the switcher binding uses Escape as a prefix, the handler yields so `Esc` then `Tab` still opens the switcher from chrome; use **‹ Grid** to go back. Sessions opened from the sidebar, a ticket, or a deep link are unchanged.

- CROW-1153 — **Session grid.** A new top-level board (`#/grid`) shows up to 16 sessions at once so a fleet can be watched without tabbing. Each cell is a read-only capture-pane snapshot of that session's managed terminal (not a live PTY — 16 attaches would SIGWINCH the shared tmux window; [ADR 0022](docs/adr/0022-session-grid-snapshots.md)). Pin from the session menu or the cell header; pins persist per browser and lead the roster, with active sessions auto-filling the rest. Overflow paginates rather than shrinking cells. Click a cell to open the full session. Web (and the Tauri shell that loads it) only.

- CROW-1149 — Ticket-board **Start Exploring**: a split-button next to **Start Working** bootstraps the same worktree / session / agent path with a read/explain-only seed prompt (no edits, no PR, no In Progress board move). A `crow:explore` label on the auto-create watcher (same toggle as `crow:auto`) dispatches that path; if both labels are present `crow:auto` wins and both are stripped. Explore is a tag on `.work` (`Session.isExplore`), not a new session kind. CLI siblings: `crow explore-issue` / `crow batch-explore-issues` (existing RPCs with `explore: true`). Worktrees are named `{repo}-{n}-explore-{slug}` so a later Start Working does not collide.

- CROW-1150 — **Signed + notarized macOS releases.** `v*` GitHub Releases of `crow` and `crowd` are signed with a Developer ID Application certificate (hardened runtime + timestamp) and notarized via `xcrun notarytool` using an App Store Connect API key — the same secret shape as radiusmethod/socketzero, without electron-builder. `scripts/macos-sign-notarize.sh` imports the `.p12` into an ephemeral keychain, signs every Mach-O in the release tree, re-packs the tarball, writes a zip (the notarized container; a zip cannot be stapled), and deletes the keychain in an `EXIT` trap so the cert never lands in the login keychain. Missing secrets fail the job rather than publishing an unsigned build. Local `make daemon` stays unsigned. `crowd` is signed standalone because launchd (`crow autostart install --binary`) execs it directly; there is no `.app` in this cut (ADR 0010 retired the SwiftUI app; the Tauri window does not yet bundle `crowd` as a sidecar). Default runner is GitHub-hosted `macos-15`; repository variable `CROW_SIGNING_RUNS_ON` retargets the job to `[self-hosted, macOS, signing]` once the native-host runner is provisioned through `corveil/corveil-ci`. Human prereqs and secret names: [docs/macos-release-signing.md](docs/macos-release-signing.md). Decision record: [ADR 0021](docs/adr/0021-signed-notarized-macos-releases.md).

- CROW-1126 — **Migrate manual Corveil gateways to the connection.** The first-class Corveil integration (epic #1117) makes `corveilConnection` the source of truth from which the AI gateway is derived, but installs that predate it still carry a hand-entered `x-citadel-api-key` gateway with no tie to an org, no rotation, and no revoke handle. Two local-only verbs bridge that gap. `crow corveil detect-gateways` scans the Manager and every workspace gateway for the `x-citadel-api-key` header and classifies each against the stored connection — `managed` (already equals the connection's derived gateway for a provisioned org), `linkable` (a plaintext key on the connection's base URL), or `manual` (with a `reason`: no connection, an `op://` value, or a base URL that doesn't match) — printing only a redacted key prefix, never the value. `crow corveil link-gateway (--workspace N | --manager) --org ID` then **adopts** a linkable gateway's existing plaintext key into the connection as that org's key: non-disruptive (the running key is unchanged) and offline, since the Corveil backend has no key→org lookup so the org is user-supplied. The adopted key is stored with an empty `keyID`, which is also the upgrade path — a later `corveil select-org` mints a real, revocable managed key in its place. `link-gateway` enforces the same precondition `detect` advertises as `linkable`: it refuses an `op://` value or a base URL that doesn't match the connection (trailing slashes ignored, like the rest of the Corveil stack), and it refuses to overwrite an org that already holds a **minted** key rather than silently dropping the handle `deselect-org` revokes by — retire that one with `deselect-org` (which revokes on Corveil) first, then link. Both verbs sit on the one local-only Corveil surface (ledger, lane, `localOnlyDenial`), and the AI-gateway docs, a new [ADR 0020](docs/adr/0020-first-class-corveil-integration.md), and the CLI reference are updated alongside.

### Changed

- CROW-1001 — Codex sessions show the **remote-control badge**, because they were always remotely drivable and the badge was the only thing saying otherwise. `OpenAICodexAgent.supportsRemoteControl` was `false` on a recorded reason — "Codex doesn't do remote control", elaborated in the matrix as "Codex's TUI isn't stdin-drivable the way `crow send` fakes RC for the others" — that was wrong in both halves, and wrong about *Crow*, not about Codex. `crow send` never writes stdin: `TerminalRouter.send` → `TmuxBackend.sendText` is tmux `load-buffer` → `paste-buffer` → `send-keys Enter`, a paste into the pane, so "this TUI refuses stdin" would not have implied undrivable even if it were true. And Codex accepts the paste — verified end-to-end in a live pane on `codex-cli 0.141.0`: the payload lands in the composer verbatim and the trailing Enter submits it (a `/status` round-trip returned the session panel). Nothing gated on the flag either — `TerminalRouter.send` is agent-agnostic, and `supportsRemoteControl` feeds only `remoteControlActiveTerminals` and the `remote_control_available` payload — so this fixes a **false-negative badge**, not a missing drive path: anyone who ever typed into a Codex session from Crow's web UI was already exercising the capability the UI denied. Codex now sits on the same footing as Cursor/OpenCode/Grok/Antigravity, where `true` has always meant "*Crow* can drive this", not "the harness ships an RC protocol". **No launch text changes** — Codex has no `--rc` and `autoLaunchCommand` still ignores `remoteControlEnabled`; a test pins that across every `SessionKind` plus the Manager launcher, so a future flag can't be added on the assumption the badge implies one. **Native `codex remote-control` was evaluated in the same pass and declined**, which is the other half of the ticket: `remote-control start` refuses on the npm build Crow resolves (it demands the managed standalone install at `~/.codex/packages/standalone/current/codex`, obtained via a different installer); `codex app-server daemon` is a machine-global singleton bound to one fixed control socket with no port/instance flag, so Crow's N concurrent per-worktree sessions cannot be addressed individually — the Codex hooks `cwd`-collision defect relocated onto the drive path; and `--remote` attaches a *local* TUI to a *remote* app server, the reverse of what the badge claims, since Crow already **is** the remote surface (browser → `crowd` → tmux). Those were probed on the installed `0.141.0` while stable was `0.147.0`, so the pin is honest about which blockers age: the direction argument is architectural, the other two are version-specific and are exactly what `0.147.0`'s added `remote-control pair` subcommand might move. None of it gates the badge, which rests on the paste path. Two things fell out of the same probe: Codex's live pane reported `alternate_on=0`, so its `usesAlternateScreen = false` is now **verified** rather than inherited from the inline default, and 0.141.0 gates a fresh directory behind *two* prompts — folder trust (which `CodexTrustSeeder` handles) and a newer hook-trust prompt listing Crow's global `~/.codex/hooks.json` entries, which is untested against unattended auto-launch and is noted in the gap audit as the next probe if a Codex `.job` ever stalls at startup. **One behavioural side effect, and it is a fix:** `/rename` passthrough now actually reaches Codex worker sessions. `agentRenameTargets` routes a Manager to its command-bearing terminals but sends work/job/review renames through `remoteControlRenameTargets`, i.e. `remoteControlActiveTerminals` — which Codex terminals never entered while the flag was `false`. So renaming a Codex work session forwarded nothing, even though the matrix's rename row read ✅ and `sessionRenameSlashCommand` returned a real `/rename`. With the flag `true` and `remoteControlEnabled` on, it lands. The paste can still only reach agent-launched terminals (`launchAgent` is what populates that set), so no Shell tab receives a `/rename`.

- CROW-999 — Codex `PostToolUse` hooks fire **async** when the installed `codex` is new enough. Upstream honored `async: true` from **0.148.0**; through `0.147.0` the hook engine parsed the key and then **skipped the entry**, so an async hook wasn't slower, it was *absent* — and since Crow's session-state detection runs on those hooks, emitting one would have silently frozen the state card. That is why `CodexHookConfigWriter.asyncEvents` sat empty since v0.139.0, and why the fix is a gate rather than a flag flip. `CodexVersionProbe` runs `codex --version` once at boot (hard-bounded by the same 3s race `BinaryIdentityProbe` uses, so a hung binary can't stall startup), parses it, and only clears the gate at `>= 0.148.0`. **Every uncertain answer lands on sync** — no Codex registered, no binary resolved, a spawn failure, a timeout, an unreadable banner — because sync is correct on every build and costs only latency, while a wrong `async` costs the hook. The gate also **rejects pre-releases of the pin**: async landed at `0.148.0-alpha.9`, so `0.148.0-alpha.1` is a build that would still drop the hooks, and standard semver precedence (a pre-release sorts below its release) rejects the whole alpha series without a special case — it starts passing on its own when the stable ships. Only `PostToolUse` is async, mirroring Claude: `PreToolUse` stays synchronous so it is *accepted* by the daemon ahead of the `PermissionRequest` that follows it, and making it async would widen precisely the inversion that does **not** self-heal (#903 — a `PreToolUse` applied after `PermissionRequest` clears the permission badge while the agent is parked at a prompt, with no further event until the user answers). A downgrade is handled: each event's entry is rebuilt whole on every boot, so a machine that stops clearing the gate has the `async` key **removed** rather than stranded. Probed once at boot like agent availability, so upgrading `codex` under a running `crowd` needs a restart. Semver parsing moved into CrowCore as `AgentSemVer`, shared with OpenCode's `--auto` window probe — with whole-token matching, so a `--version` preamble naming a path like `…/node/v22.22.2/bin/codex` can't be misread as the agent's version. **Not yet verified empirically:** the async *timing* (state-card correctness for `.job`/`.work`, no double-count against the `notify` bridge) has no observed pass, because `0.148.0` has not shipped stable yet — on 2026-08-13 npm's `latest` is `0.147.0` and `0.148.0-alpha.14` is the newest build, which the gate rejects. So this ships **inert on every stable install** and begins emitting `async` on its own once the release lands; that first stable is where the timing pass belongs.

- CROW-1002 — The session switcher's default binding is **`cmd+/`**, and **`shift+tab` is now refused outright**. `esc+tab` (CROW-980) fixed the Shift+Tab collision by making Esc a prefix, but a two-key sequence is a poor fit for the thing you reach for while reading a terminal: it arms on a 1.5s timer, any intervening keystroke breaks it, and because a prefix chord holds nothing down it can't commit on release — the overlay stays up until Enter. `cmd+/` is an ordinary modifier chord, so it opens on press and commits on release of Cmd the way a macOS app switcher does, with no timer and nothing to arm. It is also inert in the terminal: macOS produces no key data for a Cmd chord in xterm, so capturing it leaks nothing to the PTY. The sequence machinery is untouched and `esc+tab` remains a legal binding — it merely stopped being the default, so an install that has it keeps it. On a keyboard with no Cmd, set `ctrl+/`. One cosmetic consequence: the hint line separator moved from `/` to `or`, since the default's cycle key *is* `/` and "`/ / ←→ to cycle`" reads as a typo.

- CROW-980 — The session switcher's default binding is **`esc+tab`** (tap Esc, then Tab), not `shift+tab`. Shift+Tab is already Claude Code's permission-mode cycle, and `switcher.captureInTerminal` defaults to **true**, so the old default ate that keystroke inside every focused terminal. Esc is not a modifier, so this is not a string swap: a leading `esc` is now parsed as a **prefix key**, and `parseSwitcherBinding` returns it separately from `shift/ctrl/alt/meta`. Without that, `esc+tab` would have parsed identically to bare `tab` — every unmodified Tab opening the overlay and, in the terminal, Tab-completion going dead. The prefix arms for 1.5s and is broken by any intervening keystroke (a bare modifier excepted, since a resting Shift shouldn't cancel the sequence), and **Esc itself is never swallowed** — it has to stay instant for interrupting an agent, so it reaches the terminal on the way through and the overlay opens on the Tab that follows. A prefix chord holds nothing down, so it can't commit on release the way `shift+tab` does: the overlay stays open, Tab/←→ cycle, **Enter** (or a click) switches, Esc cancels — which is the ticket's reason for choosing this chord. The hint line under the strip states whichever gesture the configured chord actually uses. Existing installs are untouched: the new default reaches only a config with no `switcher.binding`, and `crow ui set --switcher-binding shift+tab` restores the old one. **Superseded within this same unreleased block by CROW-1002**, which moves the default again (to `cmd+/`) and closes the two holes this entry's last sentence describes: leaving existing installs untouched is precisely what left them eating Shift+Tab, and restoring the old binding is no longer possible — it is reserved.

- CROW-1144 — Grok **`.work` sessions open the interactive TUI immediately** instead of running the whole ticket headlessly first. Crow launched seeded Grok work sessions as `grok --prompt-file <seed>; grok -c`, on a 2026-07-25 probe that claimed every prompt form — even a positional — forced headless mode. That is false for grok **1.0.5**: `-p`/`--prompt-file` are single-turn *headless* (a "turn" is a full agentic loop, many tool calls, then exit), and positional `[PROMPT]` is *"Initial prompt for the interactive session"*. Lived failure: the pane streamed headless narration, `grok --prompt-file` was still running 10+ minutes later, and `; grok -c` never started — Crow's terminal record was `agentLaunched`, so the bug was the command shape, not the pane. Seeded `.work` (workspace skill `launch_grok` + `GrokLauncher.launchCommand`) now uses `evalPromptLaunch` with `--` so `grok -- "<prompt>"` opens a steerable TUI from turn one. Guarded at 128 KiB (`GrokLaunchArgs.argvPromptByteLimit`, mirrored in `setup.sh`); a larger seed falls back to the headless chain rather than `ARG_MAX`. Unattended `.job`/`.review` keep `--prompt-file` then `-c` — jobs need `crow send` follow-ups and reviews need a human-gated `gh pr review`. The "one turn and exits" `GrokLaunchArgs` doc-comment is retired; [ADR 0015](docs/adr/0015-harness-capability-tiers.md) records the amendment.

- CROW-1047 — Wheel-up in a Claude Code session no longer **snaps to the start of the transcript**. Two independent paths caused the same symptom. (1) **Alt-buffer latch cap-to-0:** while an alt-buffer build is still unlatched, xterm keeps the transitional 50k; wheel-up walks that local buffer; when CROW-1023's poll finally latches and `applySurfaceScrollback` caps to 0, truncating mid-history resets `ydisp` to 0 on the oldest surviving lines — session start. The cap now **defers until `viewportY` reaches `baseY`**, then applies on the next bind. (2) **SGR burst:** line/page `deltaMode` values could yield many notches per DOM event; forwarded as repeated `\x1b[<64;1;1M` reports, Claude's mouse-tracking scroll flew to the top. `wheelNotches` now magnitude-snaps line and page mode like pixel mode (one detent in → one notch out). `hydrateWhenIdle` also skips every `agent_surface` as defense in depth beside CROW-1048's `fireScrollbackCapture` gate. Cursor/shell wheel behavior unchanged.

- CROW-1035 (reopened) — Switching back to a Claude Code session no longer parks the caret below the input box, and switching to Cursor no longer stacks footer chrome or shifts the viewport a line. #1036 moved agent tab/session switches in-place instead of the #673 full reload, but still called `term.reset()` before `select-window` and still replayed CROW-606 scrollback for inline agents. `term.reset()` clears parser state tmux re-sends only as deltas (same class of bug as CROW-1043's dead wheel), so an alt-buffer Claude's live redraw after reset misaligned the TUI; inline agents got a `capture-pane` dump racing the live attach — the same stacking #1048 fixed for mid-session hydrate. In-place switches now clear with `ESC[H ESC[2J ESC[3J]` instead of reset and send `select-window` with `replay: false`; connect/reload/heal paths are unchanged. Plain shell tabs still take the full reload.

- CROW-1048 — Cursor idle/prompt chrome (tips, model line, cwd) no longer **stacks a second copy** after ordinary tool output. #1014 restored the wheel by keeping the unified 50k on inline agents (`cursor-agent` never issues smcup); that also left Cursor on the CROW-934/CROW-1026 hydrate axis a shell uses to fill holes in a thinned live stream. Cursor's live bytes *are* the transcript, so 400ms after a tool call goes quiet the idle heal re-injected a `capture-pane` replay onto an already-painted TUI — the replay tail is the chrome, the live attach paints it again. Arrival-at-top hydrate did the same thing to history, and `switchAgentWindow` arming the CROW-1027 heal added a second replay 250ms later on every in-place switch (no PTY resize to heal). Mid-session re-capture now skips every `agent_surface`; connect/reload still restore CROW-606 history and still heal a one-screen attach. xterm stays at 50k so the wheel still works — the #1008/#1009 cap is not back. Claude's alt-buffer path is unchanged.

- CROW-1043 — A Claude Code (or Manager) session no longer goes **unscrollable after switching away and back**. #1035 made an agent tab/session switch happen in place — `term.reset()` then `select-window` on the live socket — instead of the #673 full reload, which fixed the caret jump but introduced this: `term.reset()` clears xterm's `mouseTrackingMode`, and for an **alt-buffer** agent that mode is the *only* scroll path. An alt-buffer Claude has its xterm `scrollback` capped to 0 (no local buffer, no bar); the wheel works solely because `appOwnsScroll()` is `agent_surface && mouseTracking` and the tick is forwarded to Claude as an SGR wheel button (#850). The `select-window` redraw does **not** put the mode back, because tmux emits mouse-mode changes to a client as **deltas** — switching between two agent windows that share the same mouse state (Claude → Claude, or the Manager; both `mouse_any=1 mouse_sgr=1`) repaints the frame but no mouse DECSET, since from tmux's view the client already has that mode while the client just cleared it. So `appOwnsScroll()` returned `false`, the wheel fell to a zero-length local viewport, and the surface was dead to the wheel. An explicit **Reload** recovered it because a reload is a *fresh* grouped attach where tmux re-emits the full initial state (`?1000h`/`?1006h`) — and the next in-place switch killed it again, which is the "Reload fixes it, switch away and back and it's dead" report. Reproduced live against build `2.1.233`: one round-trip switch between two Claude sessions took `mouseTrackingMode` from `any` to `none` and `appOwnsScroll()` from `true` to `false`. **The daemon now re-arms the pane's actual mouse mode on every `select-window`**: `TerminalWebSocket` reads `#{mouse_standard_flag}#{mouse_button_flag}#{mouse_any_flag}#{mouse_utf8_flag}#{mouse_sgr_flag}` and yields the matching DECSET enables (`TerminalCockpit.mouseModeReArmSequence` → `?1003h?1006h` for a Claude pane) into the same stream as the replay, so the client's mode matches the pane deterministically regardless of tmux's per-client delta. It is inert where it isn't needed — a shell (or an agent idling without tracking) reports no mouse flag, so nothing is emitted, and on a non-agent surface `swallowMouseMode` drops DECSET 1000–1016 anyway — idempotent across the connect select and the CROW-934/1027 hydrate/heal re-selects, and **visually inert** (it sets an input mode and paints nothing), so unlike a scrollback replay it can't race the live frame or blank the pane. This is deliberately **orthogonal to the CROW-606 replay**, which stays skipped for an alt-buffer pane: an alt-buffer Claude has `history_size=0`, so there is no unified scrollback to restore — the dead wheel was the mouse mode, not the replay. Inline agents and shells (`alternate_on=0`) are unaffected: their replay already runs and their wheel scrolls the local viewport regardless of mouse mode.

- CROW-1035 — Switching to a Claude Code session no longer parks the caret below the input box, and switching to Cursor no longer stacks a second copy of the footer chrome. Session/tab switch on an **agent** surface was taking the #673 full reload: a new PTY at tmux's default 24×80, a SIGWINCH to the real size, then a `capture-pane` replay injected into the same stream as the live attach redraw. On an alt-buffer pane `capture-pane` is only the current frame, so that second paint left xterm's cursor — and Claude's idea of the layout — one row below the TUI. Cursor (inline) got the same-size SIGWINCH as a reprint and a doubled last line. Agent tabs now switch in place (`clearTermBuffer` + `select-window` with `replay: false` on the live socket, no new PTY). The daemon also skips the CROW-606 replay when `#{alternate_on}=1`; the live attach already has the frame. Plain shell tabs still take the #673 reload, and the header/right-click Reload button is unchanged. *(Superseded within this unreleased block by the reopened fix above, which addresses the regression after #1043/#1046/#1048.)*

- CROW-1002 — Shift+Tab reaches the agent again, so Claude Code (and Cursor, and Codex) can cycle permission modes. CROW-980 moved the switcher off `shift+tab` by changing the **default**, and a default reaches only a config with no `switcher.binding` key at all — every install that had already written one (which is every install whose config had ever been saved, since `AppConfig` encodes the whole struct) kept the old value and went on swallowing the keystroke in every focused terminal, `captureInTerminal` being true by default. The symptom was indistinguishable from an agent bug: the chord did nothing, in every session, on a Crow that had shipped a changelog entry saying it was fixed. Three changes so it cannot recur. **The chord is reserved**: `SwitcherSettings.reservedBindings` names it, `crow ui set --switcher-binding shift+tab` is rejected with an explanation rather than stored, and a config still carrying it is migrated to the default on decode — matched case-folded and trimmed, since the setter stores the string verbatim while the client parses it case-insensitively, so `Shift+Tab ` would otherwise slip past as the same swallowed keystroke. Migration and validation deliberately share one set: a binding the decoder silently rewrites but the setter still accepts would revert on the next daemon start with nothing to explain why, which is a worse bug than the one being fixed. **The terminal keeps it regardless of configuration**: `switcherCapturesInTerminal()` subtracts the reserved chords from the `captureInTerminal` preference, so both key paths — the document-level capture listener and xterm's `attachCustomKeyEventHandler` — hand Shift+Tab to the PTY even when a hand-edited `config.json` asks for capture, and even in a browser still holding the pre-migration config it was handed before the daemon restarted. The gate is chord-scoped, not a blanket opt-out: it compares parsed chords (modifiers *and* prefix), so a bare `tab` and `esc+tab` are correctly left alone, and every non-reserved binding is still captured on the same path. **Only the binding is rewritten** — the rest of a user's switcher settings survive the migration, and any binding that isn't reserved is a real choice and is left alone. Worth knowing for anyone who liked the old chord: there is no way to get it back, by design. It buys one keystroke for a control that already has three other ways in (the sidebar, a click, the configured chord outside the terminal), and costs the agent a control with no alternative binding at all.

- CROW-969 — Gateway header values wrapped in literal quotes are rejected instead of silently breaking every Claude session. A value saved as `"Bearer sk-…"` — a shell-quoting slip, two characters longer than it should be — was stored and transmitted verbatim: `validateHeaderLine` checked only for newlines and a colon, `GatewayResolver.serializeHeaders` interpolated it as-is, and `ClaudeLaunchArgs.gatewayEnvPrefix` shell-quoted the whole value, so the stray quotes survived intact into `ANTHROPIC_CUSTOM_HEADERS`. Claude Code sent a malformed credential, the gateway rejected it, and the agent reported a bare **"API error"** naming nothing — not the gateway, not the workspace, not the header. The failure was also **invisible for as long as the role ran on Cursor**: `CrowCursor` (like `CrowOpenCode` and `CrowAntigravity`) never applies the workspace gateway at all, so a config broken months ago becomes a hard failure the moment `agentsByKind.review` is cleared to `claude-code` — which reads as an agent bug rather than a config one. The rule is now two predicates on `WorkspaceGateway` in CrowCore, shared by the CLI's `validateHeaderLine` and by `SecretRoutes.buildGateway` — the one server-side chokepoint that sees the final header map from **both** the `gateway-set` RPC and the web editor's `/config/*-gateway` POSTs, so the CLI and the browser can't drift on what they accept or what they say. A value is rejected when it is wrapped in a matching `"` or `'` (two characters minimum, so a lone quote isn't read as matching itself); a *name* is rejected for a `"` anywhere, since RFC 9110's `tchar` excludes it outright, and for a **leading** `'` only, since `'` is a legal token character. That name rule is not redundant: quoting the whole pair (`--header '"X-Api-Key: sk-…"'`) splits on the first colon into a name and value where **neither half is individually wrapped**, so nothing else catches it. Deliberately still accepted: blank values (the load-bearing "keep the stored secret" signal that lets a base URL change without restating credentials), interior quotes, JSON-ish values, and `op://` references. Three places the check deliberately does **not** live — `SecretsRPC.decodeHeaderLines`, which runs strictly upstream of `buildGateway` and would shadow its message; `WorkspaceGateway.init(from:)`, where a throwing decode makes `ConfigStore.loadConfig` return nil and the next write replaces every workspace, job and credential with defaults; and `mergingPreservedHeaders`, which substitutes *stored* values for blank ones, so checking there would make the documented base-URL-only edit fail on any pre-existing bad secret and lock the user out of fixing the very config the rule exists for. Values **already** stored this way still launch and are warned about rather than repaired: stripping would mean guessing the quotes aren't part of the secret, and a loud rejection at the gateway beats authenticating with a credential nobody verified. The warning is checked before the `op://` branch on purpose — quotes around a reference defeat `hasPrefix("op://")`, so it silently falls into the plaintext arm and is never resolved at all, which is the most confusing case of the lot.
- CROW-969 — Gateway resolution says which workspace it picked, and how. `workspaceGatewayResolved` matched a workspace two ways and then discarded it, so nothing reported where a session's gateway came from. The match is now a pure `SessionService.gatewayMatch(worktreePath:prLinks:devRoot:config:)` that both the launch path and `crow get-session` share. Every Claude launch and handoff logs one line naming the workspace, which lookup claimed it (`worktree_path` or `repo_slug`), the base URL, and the header **names** — never values; `get-session` gains `workspace_id`, `workspace_name`, `workspace_match`, `gateway_set` and `gateway_base_url`, following `WorkspaceRPC.workspaceJSON`'s redaction exactly because `get-session` is *not* in `localOnlyDenial` and a remote `/rpc` peer reads it (header names and values stay with the local-only `crow gateway get`). Manager sessions report their own gateway under `workspace_match: "manager"` rather than an empty workspace match, which would have recreated this ticket's blind spot inside the tool built to close it. This makes visible a divergence that previously had to be inferred: work and job sessions resolve **by worktree path** while review clones resolve **by repo slug** (the CROW-891 fallback, since a review clone lives under `crow-reviews/` and path math names no workspace), so a repo cloned under one workspace but claimed by another workspace's `alwaysInclude` gets a *different gateway* depending on session kind — which is why reviews could fail while work sessions on the same repo, on the same machine, kept working. Carrying the matched workspace's gateway even when it is nil also separates "no workspace claims this session" from "a workspace claims it and has no gateway": identical behaviour (`ANTHROPIC_*` unset), different fixes, previously indistinguishable. Side benefit: the two-lookup rule is now directly unit-testable — `SessionServiceGatewayResolutionTests` previously documented that it *couldn't* be, since `ConfigStore` is all-static and ADR 0012 forbids touching the live devroot pointer, so only the individual helpers were covered and their composition never was.

- CROW-956 — Settings saves and large terminal pastes no longer die on the WebSocket frame limit. `crowd` built its upgrade channel with no WebSocket configuration, leaving NIO's frame decoder at its default `maxFrameSize` of 16 KiB; anything larger was answered with close code 1009 and a dead socket. Both `/rpc` and `/terminal` already declared `inbound.messages(maxSize: 1 << 20)`, but that ceiling was unreachable from a browser: `WSCore` measures a message against `maxSize` only while appending *continuation* frames, never the first one, and a browser sends one unfragmented frame per `ws.send()`. So `set-config` — a whole-blob replace that JSON-string-escapes the entire `AppConfig`, roughly doubling it on the wire — failed for **every** field once `config.json` passed ~8 KB (a handful of scheduled jobs gets there on its own), and pasting >16 KB into the web terminal dropped the socket and lost the paste. Both were silent and misattributed: the client reconnected a second later so the UI looked healthy, and the only symptom was a save that would not stick. The ceiling is now one shared constant (`CrowDaemon.maxWebSocketFrameSize`, 1 MiB) feeding the channel *and* both handlers, matching `SocketServer.maxMessageSize` so a request's fate no longer depends on whether it arrived over the Unix socket or the WebSocket — which is why `crow workspace edit` worked while the Settings tab did not. **A message past the new ceiling still closes with 1009, and deliberately so:** no request id is ever decoded for a message that was never assembled, so the only legal JSON-RPC reply would be `id: null`, which the client correctly treats as a notification and drops — there is nothing at that layer to correlate an error to. What changes is that the close is now legible. The client reads the close code and reports `set-config was too large for the daemon, which closed the connection (1009)` instead of a bare `rpc: connection closed` (tagged `err.rpcTooLarge` for callers, with an equivalent notice on the terminal socket); every other close still reads exactly as it did, and a 1009 still reconnects, since the limit is per-message, not per-connection. Daemon-side, an abnormal read now logs `[crowd] WARNING: /rpc read ended abnormally …` where previously there was no trace at all, and the read error is propagated rather than discarded with its task — without that, a fragmented over-limit message closed as if the client had merely gone away, so the client's own 1009 signal never fired. Note the log covers the fragmented case only: a single oversized *frame* is rejected by NIO below the handler, and the client's close code is the sole signal for it. Two side effects worth knowing: `maxFrameSize` also drives *outbound* fragmentation, so `crowd` now emits frames up to 1 MiB instead of chunking at 16 KiB, and the decoder may buffer up to 1 MiB per connection while accumulating a frame, against 16 KiB before.

- CROW-1004 — `crowd` serves a **read-only MCP surface**, so clients that speak the Model Context Protocol (Cowork locally, a Grok bot off-box) can read the board without a Crow-launched agent session. Six tools — `get_board_summary`, `list_sessions`, `get_session`, `list_stuck_sessions`, `list_tickets`, `list_reviews` — over five read RPCs. There is **no prompt-send, no session creation, and no config access**, and that is structural rather than a policy: the tool catalog is a closed allowlist with no passthrough, so an RPC method cannot be named from the wire and the local-only surfaces (`gateway-*`, `web-password-*`, `mcp-token-*`, `run-setup`, `hook-event`, host-app launches) are unreachable regardless of transport or scope. **The surface is generated from an allowlist the `ParityLedger` gates**: `RPCEntry` gained `mcp: MCPExposure`, defaulting to *not exported*, so a newly registered RPC cannot silently become a Grok-reachable tool — it stays invisible until someone types `mcp: .read(scope:)` on its ledger row, which is the diff a reviewer reads. `MCPLedgerExportTests` fails the build when a tool reads an unflagged method, when a flagged method has no tool, when an exported method is a write, or when an exported method is local-only; that last one is the acceptance criterion "local-only RPCs remain unreachable over the remote MCP path", asserted rather than inspected. **Two transports, two trust models.** `crow mcp serve` bridges stdio to the 0600 Unix socket with no token — a caller who can run it can already run every other `crow` verb, so a token would gate nothing — while off-box clients POST to `/mcp` with a scoped bearer token from `crow mcp token mint` (also in Settings → Web access, local browser only). `/mcp` is exempt from `WebAuthMiddleware` and authenticates itself, which is **stricter**, not looser: that middleware gates on the web-session cookie and is opt-in, so on a daemon with no web password it would wave anyone through, whereas `/mcp` has no tokenless path and no loopback bypass. Scopes are exactly `sessions:read` and `board:read` — no `sessions:write`, no `prompt:send`, no `admin`, not deferred but *undefined*, so a token cannot name a capability the server might later grow into — and `tools/list` is filtered **by the presented token**, since a deny-after-call still teaches the model that hidden tools exist. Tokens expire in 90 days by default (`--no-expiry` must be typed; `--expires-in 90` is rejected as ambiguous between seconds and days) and are stored as a SHA-256 hash with a displayable prefix, so there is no `--reveal` and a lost token is replaced rather than recovered. Deliberately **not** PBKDF2 like the web password: that protects a low-entropy human secret and is verified once per login, whereas a token is 32 CSPRNG bytes verified on every request, where 210,000 iterations would be a self-inflicted denial of service — same reasoning as a GitHub PAT, and constant-time compared either way. `SettingsSecrets` strips token hashes on the way to a browser and **restores them from disk on the way back**, so a `set-config` round-trip can neither mint a token nor revoke one. Two tools earn their shape rather than proxying a handler: `list_stuck_sessions` joins `list-sessions` and `list-sessions-live` — disjoint payloads, so neither answers "what needs a human" alone — and reports `waiting_on_input` / `idle_too_long` / `checks_failing` / `auto_merge_stuck` / `auto_rebase_stuck` with each verdict's own message; `list_tickets` drops the issue `body`, the one unbounded field in that payload, which would otherwise let a single long issue crowd the board out of the model's context. The server is **dual-era**: revision `2026-07-28` replaced the `initialize` handshake with per-request metadata and a mandatory `server/discover`, but it is weeks old and shipping clients still open with the handshake, so both are answered on one endpoint and the era is decided per request. See [`docs/mcp.md`](docs/mcp.md) for client setup and [ADR 0019](docs/adr/0019-read-only-mcp-server.md) for why the surface is task-shaped rather than one tool per RPC — including why this does not reverse CROW-528, which is about Crow *provisioning* MCP into harnesses, the opposite direction on the same wire.

- CROW-963 — Per-workspace review verdict severity policy. ### Internal

- CROW-876 — Deleted thirteen `EngineRouter` routes that returned an unconditional `{"ok": true}` for nothing: the five session-lifecycle verbs plus `quick-action`, `work-on-issue`, `start-review`, `promote-allowlist`, `refresh-tickets`, `refresh-allowlist`, `create-manager`, and `run-job`.
