## [Unreleased]

### Changed

- CROW-1002 — The session switcher's default binding is **`cmd+/`**, and **`shift+tab` is now refused outright**. `esc+tab` (CROW-980) fixed the Shift+Tab collision by making Esc a prefix, but a two-key sequence is a poor fit for the thing you reach for while reading a terminal: it arms on a 1.5s timer, any intervening keystroke breaks it, and because a prefix chord holds nothing down it can't commit on release — the overlay stays up until Enter. `cmd+/` is an ordinary modifier chord, so it opens on press and commits on release of Cmd the way a macOS app switcher does, with no timer and nothing to arm. It is also inert in the terminal: macOS produces no key data for a Cmd chord in xterm, so capturing it leaks nothing to the PTY. The sequence machinery is untouched and `esc+tab` remains a legal binding — it merely stopped being the default, so an install that has it keeps it. On a keyboard with no Cmd, set `ctrl+/`. One cosmetic consequence: the hint line separator moved from `/` to `or`, since the default's cycle key *is* `/` and "`/ / ←→ to cycle`" reads as a typo.

- CROW-980 — The session switcher's default binding is **`esc+tab`** (tap Esc, then Tab), not `shift+tab`. Shift+Tab is already Claude Code's permission-mode cycle, and `switcher.captureInTerminal` defaults to **true**, so the old default ate that keystroke inside every focused terminal. Esc is not a modifier, so this is not a string swap: a leading `esc` is now parsed as a **prefix key**, and `parseSwitcherBinding` returns it separately from `shift/ctrl/alt/meta`. Without that, `esc+tab` would have parsed identically to bare `tab` — every unmodified Tab opening the overlay and, in the terminal, Tab-completion going dead. The prefix arms for 1.5s and is broken by any intervening keystroke (a bare modifier excepted, since a resting Shift shouldn't cancel the sequence), and **Esc itself is never swallowed** — it has to stay instant for interrupting an agent, so it reaches the terminal on the way through and the overlay opens on the Tab that follows. A prefix chord holds nothing down, so it can't commit on release the way `shift+tab` does: the overlay stays open, Tab/←→ cycle, **Enter** (or a click) switches, Esc cancels — which is the ticket's reason for choosing this chord. The hint line under the strip states whichever gesture the configured chord actually uses. Existing installs are untouched: the new default reaches only a config with no `switcher.binding`, and `crow ui set --switcher-binding shift+tab` restores the old one. **Superseded within this same unreleased block by CROW-1002**, which moves the default again (to `cmd+/`) and closes the two holes this entry's last sentence describes: leaving existing installs untouched is precisely what left them eating Shift+Tab, and restoring the old binding is no longer possible — it is reserved.

### Fixed

- CROW-1002 — Shift+Tab reaches the agent again, so Claude Code (and Cursor, and Codex) can cycle permission modes. CROW-980 moved the switcher off `shift+tab` by changing the **default**, and a default reaches only a config with no `switcher.binding` key at all — every install that had already written one (which is every install whose config had ever been saved, since `AppConfig` encodes the whole struct) kept the old value and went on swallowing the keystroke in every focused terminal, `captureInTerminal` being true by default. The symptom was indistinguishable from an agent bug: the chord did nothing, in every session, on a Crow that had shipped a changelog entry saying it was fixed. Three changes so it cannot recur. **The chord is reserved**: `SwitcherSettings.reservedBindings` names it, `crow ui set --switcher-binding shift+tab` is rejected with an explanation rather than stored, and a config still carrying it is migrated to the default on decode — matched case-folded and trimmed, since the setter stores the string verbatim while the client parses it case-insensitively, so `Shift+Tab ` would otherwise slip past as the same swallowed keystroke. Migration and validation deliberately share one set: a binding the decoder silently rewrites but the setter still accepts would revert on the next daemon start with nothing to explain why, which is a worse bug than the one being fixed. **The terminal keeps it regardless of configuration**: `switcherCapturesInTerminal()` subtracts the reserved chords from the `captureInTerminal` preference, so both key paths — the document-level capture listener and xterm's `attachCustomKeyEventHandler` — hand Shift+Tab to the PTY even when a hand-edited `config.json` asks for capture, and even in a browser still holding the pre-migration config it was handed before the daemon restarted. The gate is chord-scoped, not a blanket opt-out: it compares parsed chords (modifiers *and* prefix), so a bare `tab` and `esc+tab` are correctly left alone, and every non-reserved binding is still captured on the same path. **Only the binding is rewritten** — the rest of a user's switcher settings survive the migration, and any binding that isn't reserved is a real choice and is left alone. Worth knowing for anyone who liked the old chord: there is no way to get it back, by design. It buys one keystroke for a control that already has three other ways in (the sidebar, a click, the configured chord outside the terminal), and costs the agent a control with no alternative binding at all.

- CROW-969 — Gateway header values wrapped in literal quotes are rejected instead of silently breaking every Claude session. A value saved as `"Bearer sk-…"` — a shell-quoting slip, two characters longer than it should be — was stored and transmitted verbatim: `validateHeaderLine` checked only for newlines and a colon, `GatewayResolver.serializeHeaders` interpolated it as-is, and `ClaudeLaunchArgs.gatewayEnvPrefix` shell-quoted the whole value, so the stray quotes survived intact into `ANTHROPIC_CUSTOM_HEADERS`. Claude Code sent a malformed credential, the gateway rejected it, and the agent reported a bare **"API error"** naming nothing — not the gateway, not the workspace, not the header. The failure was also **invisible for as long as the role ran on Cursor**: `CrowCursor` (like `CrowOpenCode` and `CrowAntigravity`) never applies the workspace gateway at all, so a config broken months ago becomes a hard failure the moment `agentsByKind.review` is cleared to `claude-code` — which reads as an agent bug rather than a config one. The rule is now two predicates on `WorkspaceGateway` in CrowCore, shared by the CLI's `validateHeaderLine` and by `SecretRoutes.buildGateway` — the one server-side chokepoint that sees the final header map from **both** the `gateway-set` RPC and the web editor's `/config/*-gateway` POSTs, so the CLI and the browser can't drift on what they accept or what they say. A value is rejected when it is wrapped in a matching `"` or `'` (two characters minimum, so a lone quote isn't read as matching itself); a *name* is rejected for a `"` anywhere, since RFC 9110's `tchar` excludes it outright, and for a **leading** `'` only, since `'` is a legal token character. That name rule is not redundant: quoting the whole pair (`--header '"X-Api-Key: sk-…"'`) splits on the first colon into a name and value where **neither half is individually wrapped**, so nothing else catches it. Deliberately still accepted: blank values (the load-bearing "keep the stored secret" signal that lets a base URL change without restating credentials), interior quotes, JSON-ish values, and `op://` references. Three places the check deliberately does **not** live — `SecretsRPC.decodeHeaderLines`, which runs strictly upstream of `buildGateway` and would shadow its message; `WorkspaceGateway.init(from:)`, where a throwing decode makes `ConfigStore.loadConfig` return nil and the next write replaces every workspace, job and credential with defaults; and `mergingPreservedHeaders`, which substitutes *stored* values for blank ones, so checking there would make the documented base-URL-only edit fail on any pre-existing bad secret and lock the user out of fixing the very config the rule exists for. Values **already** stored this way still launch and are warned about rather than repaired: stripping would mean guessing the quotes aren't part of the secret, and a loud rejection at the gateway beats authenticating with a credential nobody verified. The warning is checked before the `op://` branch on purpose — quotes around a reference defeat `hasPrefix("op://")`, so it silently falls into the plaintext arm and is never resolved at all, which is the most confusing case of the lot.
- CROW-969 — Gateway resolution says which workspace it picked, and how. `workspaceGatewayResolved` matched a workspace two ways and then discarded it, so nothing reported where a session's gateway came from. The match is now a pure `SessionService.gatewayMatch(worktreePath:prLinks:devRoot:config:)` that both the launch path and `crow get-session` share. Every Claude launch and handoff logs one line naming the workspace, which lookup claimed it (`worktree_path` or `repo_slug`), the base URL, and the header **names** — never values; `get-session` gains `workspace_id`, `workspace_name`, `workspace_match`, `gateway_set` and `gateway_base_url`, following `WorkspaceRPC.workspaceJSON`'s redaction exactly because `get-session` is *not* in `localOnlyDenial` and a remote `/rpc` peer reads it (header names and values stay with the local-only `crow gateway get`). Manager sessions report their own gateway under `workspace_match: "manager"` rather than an empty workspace match, which would have recreated this ticket's blind spot inside the tool built to close it. This makes visible a divergence that previously had to be inferred: work and job sessions resolve **by worktree path** while review clones resolve **by repo slug** (the CROW-891 fallback, since a review clone lives under `crow-reviews/` and path math names no workspace), so a repo cloned under one workspace but claimed by another workspace's `alwaysInclude` gets a *different gateway* depending on session kind — which is why reviews could fail while work sessions on the same repo, on the same machine, kept working. Carrying the matched workspace's gateway even when it is nil also separates "no workspace claims this session" from "a workspace claims it and has no gateway": identical behaviour (`ANTHROPIC_*` unset), different fixes, previously indistinguishable. Side benefit: the two-lookup rule is now directly unit-testable — `SessionServiceGatewayResolutionTests` previously documented that it *couldn't* be, since `ConfigStore` is all-static and ADR 0012 forbids touching the live devroot pointer, so only the individual helpers were covered and their composition never was.

- CROW-956 — Settings saves and large terminal pastes no longer die on the WebSocket frame limit. `crowd` built its upgrade channel with no WebSocket configuration, leaving NIO's frame decoder at its default `maxFrameSize` of 16 KiB; anything larger was answered with close code 1009 and a dead socket. Both `/rpc` and `/terminal` already declared `inbound.messages(maxSize: 1 << 20)`, but that ceiling was unreachable from a browser: `WSCore` measures a message against `maxSize` only while appending *continuation* frames, never the first one, and a browser sends one unfragmented frame per `ws.send()`. So `set-config` — a whole-blob replace that JSON-string-escapes the entire `AppConfig`, roughly doubling it on the wire — failed for **every** field once `config.json` passed ~8 KB (a handful of scheduled jobs gets there on its own), and pasting >16 KB into the web terminal dropped the socket and lost the paste. Both were silent and misattributed: the client reconnected a second later so the UI looked healthy, and the only symptom was a save that would not stick. The ceiling is now one shared constant (`CrowDaemon.maxWebSocketFrameSize`, 1 MiB) feeding the channel *and* both handlers, matching `SocketServer.maxMessageSize` so a request's fate no longer depends on whether it arrived over the Unix socket or the WebSocket — which is why `crow workspace edit` worked while the Settings tab did not. **A message past the new ceiling still closes with 1009, and deliberately so:** no request id is ever decoded for a message that was never assembled, so the only legal JSON-RPC reply would be `id: null`, which the client correctly treats as a notification and drops — there is nothing at that layer to correlate an error to. What changes is that the close is now legible. The client reads the close code and reports `set-config was too large for the daemon, which closed the connection (1009)` instead of a bare `rpc: connection closed` (tagged `err.rpcTooLarge` for callers, with an equivalent notice on the terminal socket); every other close still reads exactly as it did, and a 1009 still reconnects, since the limit is per-message, not per-connection. Daemon-side, an abnormal read now logs `[crowd] WARNING: /rpc read ended abnormally …` where previously there was no trace at all, and the read error is propagated rather than discarded with its task — without that, a fragmented over-limit message closed as if the client had merely gone away, so the client's own 1009 signal never fired. Note the log covers the fragmented case only: a single oversized *frame* is rejected by NIO below the handler, and the client's close code is the sole signal for it. Two side effects worth knowing: `maxFrameSize` also drives *outbound* fragmentation, so `crowd` now emits frames up to 1 MiB instead of chunking at 16 KiB, and the decoder may buffer up to 1 MiB per connection while accumulating a frame, against 16 KiB before.

### Added

- CROW-1004 — `crowd` serves a **read-only MCP surface**, so clients that speak the Model Context Protocol (Cowork locally, a Grok bot off-box) can read the board without a Crow-launched agent session. Six tools — `get_board_summary`, `list_sessions`, `get_session`, `list_stuck_sessions`, `list_tickets`, `list_reviews` — over five read RPCs. There is **no prompt-send, no session creation, and no config access**, and that is structural rather than a policy: the tool catalog is a closed allowlist with no passthrough, so an RPC method cannot be named from the wire and the local-only surfaces (`gateway-*`, `web-password-*`, `mcp-token-*`, `run-setup`, `hook-event`, host-app launches) are unreachable regardless of transport or scope. **The surface is generated from an allowlist the `ParityLedger` gates**: `RPCEntry` gained `mcp: MCPExposure`, defaulting to *not exported*, so a newly registered RPC cannot silently become a Grok-reachable tool — it stays invisible until someone types `mcp: .read(scope:)` on its ledger row, which is the diff a reviewer reads. `MCPLedgerExportTests` fails the build when a tool reads an unflagged method, when a flagged method has no tool, when an exported method is a write, or when an exported method is local-only; that last one is the acceptance criterion "local-only RPCs remain unreachable over the remote MCP path", asserted rather than inspected. **Two transports, two trust models.** `crow mcp serve` bridges stdio to the 0600 Unix socket with no token — a caller who can run it can already run every other `crow` verb, so a token would gate nothing — while off-box clients POST to `/mcp` with a scoped bearer token from `crow mcp token mint` (also in Settings → Web access, local browser only). `/mcp` is exempt from `WebAuthMiddleware` and authenticates itself, which is **stricter**, not looser: that middleware gates on the web-session cookie and is opt-in, so on a daemon with no web password it would wave anyone through, whereas `/mcp` has no tokenless path and no loopback bypass. Scopes are exactly `sessions:read` and `board:read` — no `sessions:write`, no `prompt:send`, no `admin`, not deferred but *undefined*, so a token cannot name a capability the server might later grow into — and `tools/list` is filtered **by the presented token**, since a deny-after-call still teaches the model that hidden tools exist. Tokens expire in 90 days by default (`--no-expiry` must be typed; `--expires-in 90` is rejected as ambiguous between seconds and days) and are stored as a SHA-256 hash with a displayable prefix, so there is no `--reveal` and a lost token is replaced rather than recovered. Deliberately **not** PBKDF2 like the web password: that protects a low-entropy human secret and is verified once per login, whereas a token is 32 CSPRNG bytes verified on every request, where 210,000 iterations would be a self-inflicted denial of service — same reasoning as a GitHub PAT, and constant-time compared either way. `SettingsSecrets` strips token hashes on the way to a browser and **restores them from disk on the way back**, so a `set-config` round-trip can neither mint a token nor revoke one. Two tools earn their shape rather than proxying a handler: `list_stuck_sessions` joins `list-sessions` and `list-sessions-live` — disjoint payloads, so neither answers "what needs a human" alone — and reports `waiting_on_input` / `idle_too_long` / `checks_failing` / `auto_merge_stuck` / `auto_rebase_stuck` with each verdict's own message; `list_tickets` drops the issue `body`, the one unbounded field in that payload, which would otherwise let a single long issue crowd the board out of the model's context. The server is **dual-era**: revision `2026-07-28` replaced the `initialize` handshake with per-request metadata and a mandatory `server/discover`, but it is weeks old and shipping clients still open with the handshake, so both are answered on one endpoint and the era is decided per request. See [`docs/mcp.md`](docs/mcp.md) for client setup and [ADR 0019](docs/adr/0019-read-only-mcp-server.md) for why the surface is task-shaped rather than one tool per RPC — including why this does not reverse CROW-528, which is about Crow *provisioning* MCP into harnesses, the opposite direction on the same wire.
- CROW-974 — Pre-submit guardrails in `crow-review-pr` block mis-targeted and verdict-inconsistent reviews before `gh pr review`. A review body that cites file paths with zero overlap against the target PR's changed-files list must not be posted (catches reviews drafted from carried-over context about a different PR). The `**Recommendation:**` line must agree with the submit flag (`Approve` ↔ `--approve`, `Request Changes` ↔ `--request-changes`). Both checks are local to the skill — advisory, like the CROW-963 verdict policy — and reach every harness through the shared `skills/crow-review-pr/SKILL.md` / `Resources/crow-review-pr-SKILL.md.template` pair (Claude reads the copied skill; Cursor/Codex/OpenCode/Grok/Antigravity read the inlined body). `scripts/check-workspace-custom-instructions.sh` now requires the guardrail section in both halves.
- CROW-963 — Per-workspace review verdict severity policy. Which `crow-review-pr` finding severities force `gh pr review --request-changes` is now a workspace setting (`reviewBlockingSeverities`) instead of prose hardcoded in the bundled skill, so a repo where Yellow means "nitpick" can request changes on Red only while a repo where Yellow means "should fix" keeps blocking on both. Settable with `crow workspace add|edit --review-blocking-severity red|yellow|green` (repeatable), readable via `workspace get`/`list`, and editable in Settings → Workspaces → Review verdict. **Unset means today's behaviour** (`red` + `yellow`), not "nothing blocks", and `--clear-review-blocking-severities` restores it by *removing* the key rather than writing a null or an empty list — the three states round-trip differently, and a null would make the whole `config.json` undecodable. An explicitly empty set is rejected on every write path: a workspace where nothing gates the verdict approves every review, and with the auto-merge watcher on merges it too. Decoding stays deliberately lenient in the other direction — a hand-edited config with an unknown severity drops it and falls back to the default rather than throwing, because a throwing `WorkspaceInfo` decode makes `ConfigStore.loadConfig` return nil and every writer's `?? AppConfig()` fallback then overwrites `config.json` with defaults. The policy is rendered into the skill body **once, before the review launch paths diverge**, so it reaches Claude (which reads the copied `.claude/skills/crow-review-pr/SKILL.md`) and Cursor/Codex/OpenCode/Grok/Antigravity (which read the whole body inlined into `.crow-review-prompt.md`) alike — hooking only the file copy would have left the inlining agents on the default rule, which is the common case whenever `agentsByKind.review` is Cursor. Both the Step 5 verdict rule and the summary table's "Verdict effect" column are generated from the same policy so the brief can't contradict itself, and a severity that stops gating still reads `Approve allowed` and is still reported in the review body — only the verdict changes. Two things this deliberately is **not**: it does not touch the Red/Yellow/Green taxonomy, and it is **advisory rather than enforcement** — the agent invokes `gh pr review` itself, so Crow renders the policy into the prompt but never sees the call and cannot validate the verdict actually posted. Worth knowing before relaxing a workspace: more PRs reaching an approved state feeds `autoMergeWatcherEnabled` and the `crow:merge` gate, so a workspace set to `["red"]` will auto-merge things it previously would not have. A regression test pins the default rendering byte-for-byte against the pre-change skill text, and `scripts/check-workspace-custom-instructions.sh` now diffs `skills/crow-review-pr/SKILL.md` against `Resources/crow-review-pr-SKILL.md.template` so the two halves (dev builds read the first, release builds the second) can no longer drift apart silently.
- CROW-938 — Detect when a newer Crow build is available by comparing the stamped `gitSha` against `corveil/crow` `main` (no release tags required). `crowd` owns the GitHub compare call, caches the result, and checks at most once per daemon start plus every ≥1 hour (configurable, opt-out via `versionUpdate.enabled`). Surfaces: `crow version --check` / `crow version check` (human summary with exit codes), `crow version get|set`, Settings → About (status + Check now), and a dismissible web banner when behind. Offline, rate-limited, `dev`, or unknown SHAs report `unknown` — never a false up-to-date.

## [0.2.0] - 2026-08-05

Backfill of merged PRs since the 0.1.0 release, grouped by theme.

### Web UI

- CROW-936 — The web UI has real URLs. Selecting a session, switching terminal tabs, opening the Ticket/Reviews/Allowlist/Scorecard boards, and each Settings tab are all addressable, so views can be linked, bookmarked, and survive a reload, and Back/Forward move between them instead of leaving the app. Routing is **hash-based** ([ADR 0018](docs/adr/0018-web-client-hash-routing.md)) — `crowd` serves the client from a table of exact literal paths with no catch-all, so under History-API routing an *authenticated* cold load of `/sessions/<id>` would 404 in the router, while an unauthenticated one renders the login page (the auth middleware answers any navigational GET with a 200), and the Tauri shell's `location.reload()` would hit the same 404. A fragment never reaches the server, so no Swift file changes. Routed navigation goes *through* the existing `selectSession` / `selectBoard` / `switchTerminal` / `openSettings` entry points rather than beside them, and `navigate()` no-ops on an unchanged hash so applying a route can't push a second history entry. Two shapes the ticket's sketch got wrong are corrected: there are four boards, not two, and Jobs is a Settings tab (`#/settings/jobs`), not a screen. A URL naming a session that no longer exists now lands on an explicit not-found card with a way back — Crow's retention reaper deletes completed sessions, so a dead link is the normal fate of a shared URL, and previously it left a blank header, an orphan "+" tab, and a frozen terminal; the same guard now also catches a session reaped *while you're viewing it*, which nothing checked before. Deep links survive the login round-trip: the auth middleware serves the login page at the requested URL, so the fragment is still in the address bar and is handed back once the password is accepted. Only the addressable view is encoded — scroll position, open menus, selection mode, and board filters stay out of the URL.

- #879 — Agent pickers now show **all** known coding agents, greying out (and disabling) the ones whose binary isn't on the daemon's PATH instead of hiding them — so a shipped-but-uninstalled agent (e.g. Antigravity) is discoverable, with a "not found on PATH — install it and restart Crow to enable" tooltip explaining why it's disabled. Covers the new-manager launch menu, the agent-handoff menu, and every Settings selector (Default agent + the four per-action overrides). `list-agents` gained `available` + `binary` fields; the launch gate is unchanged, so an off-PATH agent still can't be launched or handed off to.
- #752 — Multi-select "Start Working (N)" on the tickets board now fires a single `batch-work-on-issues` RPC, so the Manager runs one `/crow-batch-workspace url1 url2 …` (parallel setup) instead of N separate `/crow-workspace` submissions.
- #613 — Left pane paints chrome + skeleton (or cached last-known) session rows on first load before `list-sessions` returns, then swaps in real rows without a blank flash.
- #768 — Notifications for automation events are back after the native→web move: auto-workspace created, auto-merge enabled, auto-rebase pushed, auto-rebase conflicts, and config reloaded. The daemon pushes each over the existing `/rpc` socket at the moment the watcher acts; the web UI chimes and posts a browser notification, with per-event Enabled / sound / system toggles under Settings → Notifications. Conflict events use a distinct, harsher tone and are never suppressed by the "you're looking at it" focus rule.

### Automation

- CROW-876 — `mark-in-review` now moves the provider's board, not just Crow's session status. `IssueTracker.markInReview` did the real work but had no callers: its only entry point was `AppState.onMarkInReview`, which nothing assigned once the macOS app was retired (ADR 0010), so the verb silently degraded to `set-status inReview` while the web menu still gated it on `can_set_project_status` — promising a board move that never happened. That left the board pipeline with two of three legs wired (session start → In Progress via `setup.sh`, issue done → Done via `closeTask`), and `crow resync-jira` as the only route to In Review. The handler now calls the tracker like `mark-issue-done` does: board first, so a failed transition exits non-zero instead of leaving the session marked, then the session write. Preconditions and provider failures come back as typed `SessionActionError`s rather than a silent early return, which also fixed a latent defect the method carried unnoticed while dead — it resolved its backend from the bare provider enum, dropping the host for self-hosted GitLab/Corveil. A provider with no In Review status to move *to* is deliberately **not** an error: nothing was ever going to move, so the session still transitions and the response carries an additive `warning`. That covers GitLab and, more importantly, any GitHub board whose column isn't named "In Review"/"Review" or whose Status field is unset — throwing there would have turned a fix into a breakage for a large slice of real boards. **New side effect:** on a GitHub repo with no project board at all, `mark-in-review` now applies the `crow:in-review` fallback label (#706, #790) — a repo write this verb never made before. `docs/automation.md` also claimed a "PR opened → In Review" transition that no code performed; corrected rather than implemented.
- CROW-921 — A changes-requested PR whose findings were actually fixed no longer parks in `changesRequested` forever. The loop had two states and needed three: the only thing that re-requested review was a sentence inside the changes-requested prompt, and that prompt is reachable only while the agent still *owes* a fix — so it could never fire once the fix landed, and with the host's review request already consumed the PR was invisible to the reviewer's queue and to `review-requested:@me` alike. `PRStatus.changesRequestedState` now names all three (`needsRefine` / `awaitingReRequest` / `awaitingReviewer`) and both `needsRefine` and the new `applyAutoReRequestReview` watcher derive from it, so they can't drift apart. The third state is scoped to *the reviewers who requested changes*, not to "does the PR have any pending request" — requests are per-reviewer and the host clears only the submitting one, so a PR routinely carries A's blocking verdict alongside B's still-pending original request, and a PR-wide reading would silence both halves of the loop for exactly the multi-reviewer PRs this is meant to rescue. The watcher calls `gh pr edit --add-reviewer` from the daemon rather than asking the agent to — a one-line API call routed through an agent turn costs a turn's tokens, can't be verified, and would re-inherit the gate that caused the dead-end; the prompt hint stays as belt-and-braces, since re-requesting an already-requested reviewer is a no-op. Gated by `autoRespond.autoReRequestReview` (**on** by default, alongside `respondToChangesRequested`, because the prompt has always instructed the agent to do this), readable and writable via `crow automation get|set --auto-re-request-review`. Two supporting fixes: `lastSubstantiveCommitAt` now anchors on the commit **author** date rather than the committer date, closing the documented CROW-508 rebase gap in both directions — a rebase restamp no longer suppresses a genuine needs-refine, nor fires a no-op review round at a reviewer; and every *suppressed* needs-refine evaluation is now logged with the gate that held it (`needs-refine: #N gated (reason=…, state=…, lastCR=…, lastCommit=…, reviewerReRequested=…, idle=…, cooldown=…)`), rate-limited to changes plus an hourly heartbeat, where previously only firing was logged and a stuck PR left no trace at all.
- #888 — The `crow:merge` label no longer lands in silence. When Crow's auto-merge watcher can't act on a labeled PR, the reason now reaches the UI instead of only `crowd-automation.log`: `list-sessions-live` carries an additive `auto_merge_state` (`{phase, reason, message, permanent}`), and the sidebar PR pill and detail header render it as a tinted ⛙ chip in the shared PR glyph vocabulary — green enabled, purple merged by Crow, orange retrying, red permanently blocked, grey watcher-off — with the full sentence in the tooltip and `aria-label`. The twelve skip reasons (previously six enum cases plus six ad-hoc string literals) are one enum carrying the same grep-stable log strings plus a human sentence and a permanence flag; reasons the pill already renders (conflicts, changes-requested, no label) are deliberately not republished. Repo policy is now read proactively from GraphQL `Repository.autoMergeAllowed` on the fetch Crow already makes, rather than discovered by failing `gh pr merge --auto` and string-matching the error, and a repo with GitHub's "Allow auto-merge" disabled gets a **direct squash-merge fallback** for PRs that are OPEN, non-draft, `CLEAN`, `MERGEABLE`, checks-green, approved, and Crow-authored. A permanent block fires a new **Auto-Merge Blocked** notification, once per PR rather than once per 60s poll. `crow add-merge-label` still applies the label and still returns `ok: true`, but now includes a `warning` when the label can't lead to a merge. The bare untinted ⛙ in the session row's trailing cluster is folded into the PR pill, so "Crow armed this" and "Crow gave up on this" no longer render identically.
- #137 — Session analytics emitted via Claude Code's OpenTelemetry exporter (configure via `CLAUDE_CODE_ENABLE_TELEMETRY` and `OTEL_EXPORTER_OTLP_ENDPOINT`).

### Internal

- CROW-876 — Deleted thirteen `EngineRouter` routes that returned an unconditional `{"ok": true}` for nothing: the five session-lifecycle verbs plus `quick-action`, `work-on-issue`, `start-review`, `promote-allowlist`, `refresh-tickets`, `refresh-allowlist`, `create-manager`, and `run-job`.
